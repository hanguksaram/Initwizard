# Стартовый пакет методологии для инстанса Gina

Каталог, который человек (оператор) передаёт своему AI-агенту. Агент читает `HANDOFF.md` и вместе с оператором проходит **мастер установки**: собирает доступы, узнаёт, что за проект, ставит на инстанс Gina минимальную методологию разработки и настраивает наблюдение за инстансом.

Пакет не привязан ни к какому проекту. Какой это проект, где его код, задачи и интерфейс, оператор называет по ходу мастера.

Этот файл — для человека. Агенту нужен `HANDOFF.md`.

## Что получится в итоге

- В репозитории методологии — отдельная ветка с методологией, собранная малыми merge request-ами; каждый вливается только после согласия оператора.
- На инстансе Gina — порядок работы агентов: задача или просьба → разбор → реализация → ревью → merge request человеку. Три агента (`analyst`, `developer`, `reviewer`), правила четырёх служебных ролей, навыки.
- Навыки с описанием именно вашего проекта, составленные мастером по вашим ответам и, если вы разрешите, по исследованию кода, сборок, правил кода и интерфейса.
- На машине агента — сторож инстанса: по расписанию снимает состояние инстанса и сообщает о сбоях.
- Итог обычным текстом: что сделано, что пропущено, что не проверено, и ответы на частые вопросы.

## Как начать

1. Склонируйте репозиторий на машину, где работает ваш AI-агент.
2. Откройте сессию агента в корне каталога и скажите: **«прочитай HANDOFF.md»**.
3. Дальше агент ведёт сам: объясняет каждый шаг и спрашивает согласие на всё, что что-то меняет.

Сессию можно прервать в любой момент: ход записывается в журнал `state/wizard.json`, новая сессия продолжит с того же места.

## Что понадобится

На машине: `python3` 3.9+, `kubectl`, `git`, `curl`; сеть до GitLab с репозиторием методологии, до инстанса Gina и до API Kubernetes.

Обязательные доступы (значения вы вписываете в файлы сами, в чат их присылать не нужно):

| Доступ | Зачем |
|---|---|
| Адрес инстанса Gina и токен владельца | читать настройки, проверять ветку без применения, переключить инстанс на новую ветку, создать один регламент |
| Токен GitLab (область `api`, роль не ниже Developer) | создавать ветку и merge request-ы в репозитории методологии |
| Репозиторий методологии | где хранить методологию; существующие ветки не читаются и не меняются |
| kubeconfig и имя пространства инстанса | читать состояние подов и журналы; желательно право `exec` |

Необязательные: PostgreSQL и ClickHouse инстанса на чтение, канал тревог, прямой доступ к Jira, тестовая учётная запись интерфейса продукта. Без каждого из них мастер работает, но говорит, что именно становится недоступно.

Секреты лежат в `~/.gina-poc` (права 700, файлы 600), вне этого каталога. Шаблоны файлов — в `wizard/secrets-templates/`.

## Как выписать персональный токен API Gina

Персональный токен — ключ к API инстанса, привязанный к вашей учётной записи и одному проекту. Его выпускаете вы сами в интерфейсе Gina. Агенту он нужен, чтобы читать настройки инстанса, отправлять поручения и следить за работами.

1. Откройте интерфейс инстанса и войдите своей учётной записью: `https://<адрес инстанса>/ui/overview`.
2. Перейдите в **«Настройки»** (последний пункт бокового меню, адрес `/ui/interface`). Нужен раздел **«Персональные токены API»** в группе «Настройки этого браузера».
3. Заполните форму:
   - **Название** — по нему вы потом узнаете токен в списке, например `ai-agent-<машина>`;
   - **Срок действия, дней** — по умолчанию 30;
   - **Права доступа** — отметьте только нужные. Для мастера и сторожа достаточно чтения промптов («Промпты, исполнители и навыки»; изменить их по токену нельзя, только через Git), чтения и записи «Работ» и «Входящих задач», чтения и записи «Расписаний» (мастер создаёт один регламент). По желанию добавьте чтение Postgres и ClickHouse. Остальные права — Mattermost, интеграции, GitLab методологии, Kubernetes, LiteLLM — мастеру не нужны.
4. Нажмите **«Создать токен»** и сразу скопируйте его. Сервер хранит только хеш токена, поэтому позже показать его ещё раз он не сможет.
5. Вставьте токен в файл `~/.gina-poc/gina.env`, в строку `GINA_OWNER_TOKEN=`, а в `GINA_URL=` впишите адрес инстанса без пути. Права на файл — `600`. Токен не присылайте в чат.
6. Скажите агенту «готово». Он проверит токен командой `python3 scripts/access_check.py --only gina`.

Как токен живёт дальше:
- В разделе виден список выпущенных токенов: права, дата создания, срок действия и время последнего использования. Ненужный токен отзывается кнопкой **«Отозвать»**.
- Когда срок истечёт, выпустите новый токен и замените им строку в `gina.env`.

Что персональный токен не может (проверено 19.11.2026):
- Предпросмотр ветки методологии на инстансе (`POST /api/prompt-source/preview`): ответ `403 personal_token_scope_required`, и ни одно право в форме этого не разрешает. Переключение инстанса на новую ветку тоже не проверялось — по описанию в интерфейсе промпты по токену только читаются.
- Чтобы пройти шаг 3 мастера, нужен токен владельца инстанса от администратора платформы. Другой вариант: эти действия выполняются из вашей сессии в интерфейсе. Агент может войти под вашей учётной записью через браузер без окна, но только с вашего отдельного согласия (см. `HANDOFF.md`, раздел «Персональный токен API Gina»).

## Шаги мастера

| Шаг | Что происходит |
|---|---|
| 1. Доступы | агент запрашивает доступы по одному, объясняет зачем и сразу проверяет |
| 2. Проект | вопросы о проекте; по вашему согласию — исследования только чтением; составление навыков проекта |
| 3. Методология | новая ветка с пустого каталога, накат по одному элементу, переключение инстанса, регламент побудки по сборке |
| 4. Сторож инстанса | настройка под выданные доступы, интервал, тихие часы |
| 5. Итоговая проверка | один прогон по всему установленному |
| 6. Итог и FAQ | что сделано и как работать дальше |
| 7. Запуск сторожа | включение расписания |

### Шаг 2 подробнее: как пакет узнаёт проект

Сначала паспорт с ваших слов: название, что делает продукт, где код, где задачи, адреса интерфейса, пространства стендов, канал команды, ревьюер, владелец. На «не знаю» агент оставляет поле пустым.

Затем шесть необязательных исследований. Каждое только читает и запускается по отдельному согласию:

| Исследование | Что читает |
|---|---|
| Кодовая база | список репозиториев, языки, ветки, корневые каталоги, README |
| Сборки | конфигурацию CI, последние сборки и причины отказов |
| Правила кода | документы стандартов, настройки линтеров и форматирования |
| Среда исполнения | пределы подов исполнителя и установленные в них инструменты |
| Трекер | типы задач, статусы, доступные переходы |
| Стенды и интерфейс | ответы адресов; обход разделов браузером без окна, только по ссылкам |

По итогам агент составляет навык `project` (всегда) и, если есть из чего, `code-conventions` и `product-ui`, и показывает их вам до установки. То, что не исследовалось, записывается одной строкой «не исследовалось».

### Что ставится в зависимости от проекта

| Признак | Когда включается | Что добавляет |
|---|---|---|
| `gitlab` | к инстансу подключён GitLab, и код проекта лежит в нём | навыки `gitlab`, `build-watch`, регламент побудки по сборке |
| `jira` | к инстансу подключена Jira, и назван проект | навык `jira` |
| `code_conventions` | в репозиториях найдены правила кода | навык `code-conventions` |
| `product_ui` | интерфейс пройден или его карта выведена из кода | навык `product-ui` |

Всего 17 элементов наката. Неприменимые агент показывает с причиной и не ставит.

## Как пакет бережёт инстанс

- Каждое влитие, переключение инстанса, создание и включение регламента — по отдельному согласию. Дословный ответ оператора пишется в журнал и показывается в итоге.
- Перед влитием делается предпросмотр: инстанс разбирает ветку и сообщает об ошибках, ничего не применяя.
- Пока инстанс не переключён на новую ветку, она ни на что не влияет. Прежний источник методологии сохраняется и возвращается одной командой.
- Исследования проекта ничего не меняют. В интерфейсе продукта открываются только ссылки.
- Агенту запрещено додумывать факты: оператору он говорит только то, что напечатала команда или что записано в журнале.

## Состав каталога

```
README.md                  этот файл
HANDOFF.md                 вход для AI-агента: правила мастера и таблица шагов
wizard/                    шаги мастера и шаблоны файлов секретов
methodology/ROLLOUT.json   порядок и цели элементов наката
methodology/files/         базовые тексты: roles/, agents/, skills/
methodology/templates/     шаблоны навыков проекта
methodology/automation-templates/   определение регламента побудки по сборке
scripts/                   журнал мастера, проверка доступов, сбор фактов о проекте, накат, переключение источника, итоговая проверка
watcher/                   сторож инстанса: эталон, образец настроек, текст регулярного разбора
docs/                      словарь для разговора с оператором, обоснование набора
```

Каталог `state/` и рабочие файлы сторожа создаются при прохождении мастера и в репозиторий не попадают.

## Что проверено и что нет

Проверено:
- сбор фактов о проекте — только чтением, на одном живом инстансе Gina с GitLab и Jira за прокси;
- накат, переключение источника и регламент — на локальной имитации GitLab и Gina, в двух вариантах: все признаки включены и все выключены.

Не проверено:
- **запись в настоящие GitLab и Gina не выполнялась ни разу.** Имитация не подтверждает договор с настоящим API, поэтому каждый шаг мастера сверяет результат и останавливается при расхождении;
- работа агентов по установленной методологии — подтверждается только пробным запуском после установки;
- вход в интерфейс продукта под учётной записью;
- сторож на вашем инстансе: в пакете он эталон, шаг 4 обязывает подогнать его.

Полный список — в `docs/DESIGN.md`.

## Ограничения

- Готовые навыки доступа есть только для GitLab и Jira. Если код или задачи лежат в другой системе, агент скажет, что работать с ней агентам Gina нечем, и поставит остальное.
- Автоматического набора задач из трекера нет: задачу агентам называет человек в подключённом к Gina канале.
- Тестировщика, проверок на стенде и учёта расхода модели в наборе нет.

## После установки

Тот же агент остаётся рабочей сессией: разбирает выжимки сторожа, обновляет сведения о проекте, проводит правки методологии тем же путём — merge request, предпросмотр, влитие после согласия. Порядок — раздел «После установки» в `HANDOFF.md`.
