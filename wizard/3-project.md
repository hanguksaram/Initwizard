# Шаг 3. Проект

`python3 scripts/wizard_state.py step 3 start`

**Скажи оператору (своими словами):** «Базовая методология одинакова для любого проекта. Чтобы агенты работали именно с вашим, им нужны сведения о нём. Сначала я задам несколько вопросов — это быстро и обязательно. Потом предложу пять необязательных исследований: кодовая база, сборки, правила кода, среда, в которой агенты выполняют команды, и интерфейс продукта. Каждое только читает и ничего не меняет; от любого можно отказаться — тогда соответствующего раздела у агентов просто не будет. По итогам я составлю для агентов один-три текста о проекте и покажу их вам до установки».

Итог шага — файлы в `methodology/files/skills/`:

| Навык | Когда составляется | Что в нём |
|---|---|---|
| `project` | всегда | паспорт проекта по ответам оператора + разделы по проведённым исследованиям |
| `code-conventions` | если проведено исследование правил кода и в нём что-то найдено | где лежат правила кода и главные соглашения |
| `product-ui` | если проведён обход интерфейса или разобраны его маршруты в коде | карта разделов и основные сценарии |

## 3.1. Паспорт проекта (обязательно)

Задай вопросы по одному. На «не знаю» не настаивай и не подсказывай значение: оставь пустым. Каждый ответ записывай сразу.

| Вопрос | Команда записи |
|---|---|
| Как называется проект? | `wizard_state.py set project_name "…"` |
| Что делает продукт — одной-двумя фразами? | `wizard_state.py set product_summary "…"` |
| Система и адрес хостинга кода уже записаны на шаге 2. Какой путь группы или репозитория в нём? | `wizard_state.py set code_base "<группа/подгруппа или группа/репозиторий>"` (на шаге 2 не спрашивали — ещё `set code_host "…"`) |
| Трекер задач записан на шаге 2. Если нет — где ведутся задачи: какая система и какой проект в ней? | `wizard_state.py set tracker "…"`; для Jira — ещё `set tracker_project "<КЛЮЧ>"` |
| Есть ли развёрнутый интерфейс продукта? Адрес или адреса. | `wizard_state.py set ui_urls "<адрес[,адрес]>"` |
| В каких пространствах Kubernetes развёрнуты стенды продукта (если знаете)? | `wizard_state.py set product_namespaces "<имя[,имя]>"` |
| В каком канале команда пишет просьбы агентам? | `wizard_state.py set mm_channel "…"` |
| Кто ревьюер-человек для merge request-ов по умолчанию (логин)? | `wizard_state.py set human_reviewer "…"` |
| Кому сообщать о застрявшей работе и спорных решениях? | `wizard_state.py set project_owner "…"` |
| Есть ли своё правило именования рабочих веток? | `wizard_state.py set branch_rule "…"` (нет — не задавать) |

Пространство самого инстанса Gina уже задано на шаге 1 (`k8s.env`).

## 3.2. Что подключено к инстансу

```bash
python3 scripts/project_probe.py detect
```

Команда показывает, к каким внешним системам у инстанса есть прокси (подключения из шага 2) и какие каналы общения подключены. Нужной системы в выводе нет, а оператор хочет её подключить — вернись к шагу 2, раздел 2.3. По её выводу включи или выключи два признака — от них зависит, какие базовые навыки будут поставлены:

```bash
python3 scripts/wizard_state.py feature gitlab on|off "<основание из вывода>"
python3 scripts/wizard_state.py feature jira on|off "<основание из вывода>"
```

- **GitLab через прокси есть** и код проекта лежит в этом GitLab — `gitlab on`. Тогда ставятся навыки `gitlab`, `build-watch` и регламент побудки по сборке.
- **GitLab через прокси нет** или код лежит в другой системе — `gitlab off`. Скажи оператору прямо: «Готового навыка для вашего хостинга кода в пакете нет. Если подключение к нему создано на шаге 2, агенты увидят его адрес, но без инструкции; если не создано — работать с репозиторием им нечем».
- С Jira — так же: `jira on`, только если прокси есть и оператор назвал проект Jira. Иначе `jira off` и та же честная оговорка про трекер.
- Канала общения в выводе нет — скажи оператору: просьбы из чата до агентов не дойдут, пока подключение не настроено на инстансе. Настраивать его — не задача мастера.

Если команда не сработала из-за отсутствия права `exec` — она сама попробует внешний API; если и он не ответил, спроси оператора, какие системы подключены, и запиши признаки с основанием «со слов оператора».

## 3.3. Необязательные исследования

Перед каждым: скажи, что оно даёт, что читает и сколько примерно запросов делает, и спроси согласие. Отказ — запиши `wizard_state.py decision 3 "от исследования <название> оператор отказался: <причина>"` и иди дальше.

После каждого: перескажи оператору главное из вывода команды (не весь вывод) и спроси: «Что из этого неверно или устарело?» Поправки запиши как решения — они важнее собранных фактов.

### А. Кодовая база

Нужно: признак `gitlab` включён, задан `code_base`.

```bash
python3 scripts/project_probe.py repos
```

Читает список репозиториев, языки, ветки, состав корневых каталогов и начало README каждого. Код берётся через прокси Gina из пода ядра — тем же путём, каким его увидят агенты (нужно право `exec`); если так не вышло, команда пробует токен из `gitlab.env` и пишет, какой путь сработал.

Что показать оператору: сколько репозиториев, на чём написаны, какие выглядят служебными. Спроси: «Все ли это репозитории проекта? Какие не относятся к продукту?»

### Б. Сборки (CI)

Нужно: выполнено исследование А.

```bash
python3 scripts/project_probe.py ci
```

Читает конфигурацию CI каждого репозитория и пять последних сборок; у последней неудачной — причины отказа шагов.

Что показать: в скольких репозиториях есть CI; проходят ли сборки **на сегодня**; если нет — причину дословно из вывода. Не объясняй причину от себя.

### В. Правила кода

Нужно: выполнено исследование А.

```bash
python3 scripts/project_probe.py conventions
```

Ищет в репозиториях документы стандартов и настройки линтеров, форматирования и проверки коммитов; сохраняет их содержимое (первые 8 КБ каждого, не больше 30 файлов на репозиторий) в `state/project/conventions/<путь репозитория, где «/» заменён на «__»>/`; считает тестовые файлы; берёт заголовки последних коммитов.

Что показать: в каких репозиториях правила найдены, в каких нет; какие найденные файлы не прочитаны (строка «НЕ прочитано») — их назови и в навыке, в разделе «Чего не знает этот навык».

### Г. Среда исполнения

```bash
python3 scripts/project_probe.py env
```

Читает пределы памяти и процессора подов, в которых агенты выполняют команды, и (при праве `exec`) какие инструменты в них установлены.

Что показать: пределы и чего из нужного стекам проекта в поде нет. Вывод «значит, в поде нельзя запускать …» делай, только сопоставив с исследованием Б.

### Д. Трекер задач

Нужно: признак `jira` включён, задан `tracker_project`.

```bash
python3 scripts/project_probe.py tracker
```

Читает типы задач, статусы и переходы, доступные техническому пользователю Gina.

**Обязательный вопрос оператору:** «Какие переходы статусов разрешить агентам? Обычно — "взять в работу" и "передать на ревью"; закрывать задачи агентам не разрешается». Ответ: `wizard_state.py set agent_transitions "<перечень словами оператора>"`. Не ответил — агентам статусы менять нельзя.

### Е. Стенды и интерфейс продукта

Нужно: задан `ui_urls`.

```bash
python3 scripts/project_probe.py stands
```

Запрашивает адреса и, если названы пространства стендов и на них есть права, читает список подов.

Затем — обход интерфейса. Спроси отдельно: «Открою интерфейс в браузере без окна и пройду по ссылкам разделов. Я только открываю страницы: ничего не нажимаю и не отправляю. Можно?» Если в `ui.env` задана тестовая учётная запись — спроси ещё: «Войти под тестовой учётной записью из `ui.env`?»

```bash
python3 scripts/project_probe.py ui              # с входом, если учётная запись задана и оператор согласен
python3 scripts/project_probe.py ui --no-login   # без входа
```

Браузер берётся на этой машине, если в ней есть Playwright, иначе — в поде исполнителя инстанса. Результат — `state/project/ui.json`.

Что показать: что открылось по каждому адресу; выполнен ли вход; какие разделы пройдены. **Скажи честно, если пройдена только страница входа.** Если стенд не отвечает или входа нет, а в коде есть интерфейсный репозиторий — предложи вывести карту разделов из файлов маршрутов в коде и пометить её «вживую не пройдено».

## 3.4. Составление навыков проекта

Сырьё: `state/project/facts.json` (`python3 scripts/project_probe.py show`), каталоги `state/project/conventions/…`, файл `state/project/ui.json`, решения оператора в журнале.

### Правила составления (обязательны)

1. **Только из источников.** Каждое утверждение — из фактов, из сохранённого файла правил, из README или со слов оператора. Нет источника — не пиши. Назначение репозитория выводи из README и состава каталогов, а не из названия; не понял — «назначение не установлено».
2. **Дата и способ.** Первая строка навыка — когда и чем снято. У всего, что меняется (сборки, стенды), — «на дату снимка» и требование перепроверять.
3. **Непроведённое исследование — одна строка «не исследовалось»**, как подсказано в шаблоне. Не заполняй такие разделы общими словами.
4. **Не пересказывай документы целиком.** Навык указывает, где лежит правило, и выносит наверх главное. Объём: `project` — до двух экранов, `code-conventions` — до двух, `product-ui` — до полутора.
5. **Никаких секретов и учётных данных.** Адрес стенда — можно; логин и пароль — нельзя.
6. **Поправки оператора сильнее фактов.** Если оператор сказал, что репозиторий служебный или сборки чинят, — пиши так, как он сказал, с пометкой «со слов оператора».
7. В шаблонах есть строки вида `{{PROJECT_NAME}}` — их не трогай: скрипт наката подставит значения из журнала. Все пометки `<!-- ЗАПОЛНИ: … -->` должны быть заменены текстом или строкой «не исследовалось»; скрипт откажется ставить навык, в котором осталась хоть одна.

### Порядок

```bash
mkdir -p methodology/files/skills/project
cp methodology/templates/project.SKILL.md methodology/files/skills/project/SKILL.md
```

Заполни `methodology/files/skills/project/SKILL.md` по пометкам шаблона.

Навык **`code-conventions`** составляй, только если исследование В нашло правила хотя бы в одном репозитории:

```bash
cp methodology/templates/code-conventions.SKILL.md methodology/files/skills/code-conventions/SKILL.md
# заполнить, затем:
python3 scripts/wizard_state.py feature code_conventions on "составлен по исследованию правил кода <дата>"
```

Иначе: `wizard_state.py feature code_conventions off "<исследование не проводилось | правил в репозиториях не найдено>"`.

Навык **`product-ui`** составляй, только если обход интерфейса прошёл дальше страницы входа или карта выведена из кода:

```bash
cp methodology/templates/product-ui.SKILL.md methodology/files/skills/product-ui/SKILL.md
# заполнить, затем:
python3 scripts/wizard_state.py feature product_ui on "<пройдено вживую | выведено из кода, вживую не пройдено> <дата>"
```

Иначе: `wizard_state.py feature product_ui off "<причина>"`.

Проверь:

```bash
python3 scripts/validate_methodology.py
```

## 3.5. Показ оператору

Покажи оператору каждый составленный навык целиком (или предложи открыть файл) и одной фразой скажи, зачем он агентам. Спроси: «Что здесь неверно? Чего агентам о проекте не хватает?» Правки внеси в файл.

Отдельно назови:
- что **не исследовалось** и почему;
- что **не удалось прочитать** (нет прав, нет сети, закрытые источники);
- какие базовые навыки **не будут поставлены** из-за выключенных признаков и что из-за этого агенты не смогут делать.

Шаг пройден: `python3 scripts/wizard_state.py step 3 done`. Если навык `project` составлен только по паспорту, без исследований — это допустимо: `step 3 done`, а в итоге шага 7 будет сказано, что сведения о проекте минимальны.
