# Шаг 2. Подключения к внешним системам

`python3 scripts/wizard_state.py step 2 start`

**Скажи оператору (своими словами):** «Агенты Gina не ходят в ваш GitLab или трекер напрямую и не знают ваших паролей. На инстансе заводится подключение: адрес внешней системы и её ключ, который хранится в хранилище секретов инстанса. Агент обращается по внутреннему адресу Gina, а ключ подставляет сама платформа. Сейчас я посмотрю, что уже подключено, спрошу, какие системы нужны проекту, и для недостающих создам подключения. Ключ для каждого вы впишете в файл на этой машине; в чат его присылать не нужно».

Этому шагу нужен доступ к Kubernetes с правом `exec` в под ядра (шаг 1, доступ №4): подключения создаются обращением к ядру Gina изнутри его пода. Токен владельца инстанса для этого шага не нужен. Права `exec` нет — см. раздел 2.6.

## 2.1. Что уже подключено

```bash
python3 scripts/adapter_setup.py list
```

Перескажи: какие подключения есть, есть ли среди них хостинг кода и трекер задач (последняя строка вывода), по какому адресу к ним ходят агенты. Подключения, которых мастер не создавал, не трогай и не оценивай.

## 2.2. Какие системы нужны проекту

Задай вопросы по одному. Ответы запиши сразу — они же войдут в паспорт проекта на шаге 3.

| Вопрос | Запись |
|---|---|
| Где лежит код проекта: какая система и её адрес? | `wizard_state.py set code_host "<система и адрес>"` |
| Где ведутся задачи: какая система, её адрес, какой проект в ней? | `wizard_state.py set tracker "<система и адрес>"`; для Jira — `set tracker_project "<КЛЮЧ>"` |
| К каким ещё системам агентам нужен доступ для работы: документация, сервер сборок, анализ качества кода, макеты? | `wizard_state.py decision 2 "нужны подключения: <перечень словами оператора>"` |

На «не знаю» и «не нужно» не настаивай. Не предлагай системы, которых оператор не назвал.

Сопоставь ответы с выводом `list`:
- система уже подключена — скажи это и предложи проверить: `python3 scripts/adapter_setup.py check --name "<имя подключения>"`. Проверка шлёт один запрос во внешнюю систему и ничего не меняет;
- системы нет в списке — переходи к разделу 2.3 для неё;
- оператор не уверен, та ли это система, — сравни адрес из его ответа с адресом в выводе `check`; не совпадает — это другая система.

## 2.3. Подбери тип подключения

```bash
python3 scripts/adapter_setup.py types            # типы для внешних систем; --all — все типы инстанса
python3 scripts/adapter_setup.py describe <тип>   # поля настройки и вид ключа
```

- Список типов берётся с инстанса: на другой версии Gina он может отличаться. Системы нет в списке — скажи оператору прямо: «этот инстанс не умеет подключать <система>»; не подбирай похожий тип без его слова. Единственный запасной вариант — `basic-http-outbound` (произвольный HTTP-сервис с ключом в заголовке); предлагай его, только если оператор подтверждает, что у системы обычный HTTP API.
- Пометка «в пакете есть навык» значит, что агенты получат готовую инструкцию для этой системы (сейчас это GitLab и Jira). Для остальных подключение будет работать, но готового навыка нет: агент увидит только адрес и общее описание. Скажи это оператору до создания.
- Пометка «в интерфейсе» (видна с `--all`) — типы, которым нужна настройка привязки: входящие очереди задач, каналы чата, почта. Мастер их не создаёт; см. раздел 2.6.

## 2.4. Создай подключение (для каждой системы отдельно)

**1. Объясни, что нужно от оператора.** По выводу `describe`:
- адрес системы (поле `base_url`);
- ключ. Скажи оператору дословно, что написано в строке «Секрет» вывода `describe`, и добавь: «Это должна быть техническая учётная запись, а не ваша личная: под ней агенты будут читать и писать во внешней системе. Какие ей дать права — решаете вы; агентам этой установки нужно читать репозитории и задачи, создавать ветки и merge request-ы, комментировать задачи». Где и как выпустить ключ — задача оператора; способ не подсказывай.

**2. Подготовь файл ключа:**

```bash
python3 scripts/adapter_setup.py secret-file <тип> <имя-файла>
```

Команда создаёт `~/.gina-poc/adapters/<имя-файла>.env` с правами 600 и пустыми полями. Оператор вписывает значение сам и говорит «готово». Если ключ состоит из нескольких частей (логин и пароль), они вписываются по строке на часть — так, как подсказано в самом файле.

**3. Выбери имя и короткий адрес.**
- Имя — как подключение будет называться в списках: «GitLab API», «Jira API» и т. п.
- Короткий адрес (`--alias`) нужен, **только если подключение этого типа на инстансе уже есть**. У каждого типа один общий короткий адрес (например, `/gitlab`), и базовые навыки пакета ходят именно по нему. Второе подключение того же типа без собственного адреса делает общий адрес неоднозначным — агенты перестают по нему ходить. Скрипт в таком случае откажет и попросит `--alias`. Для первого подключения типа `--alias` не задавай.

**4. Покажи план без создания:**

```bash
python3 scripts/adapter_setup.py connect <тип> --name "<имя>" --base-url <адрес> --secret-file <имя-файла> [--alias <адрес>] --dry-run
```

Перескажи вывод оператору: тип, имя, адрес системы, из какого файла ключ (значение не показывается), что произойдёт.

**5. Спроси согласие:** «Создаю подключение "<имя>" к <адрес>? Ключ из файла уйдёт в хранилище секретов инстанса, агенты получат адрес для работы с системой». Запиши ожидание: `wizard_state.py position "жду согласие на подключение <имя>"`.

**6. Создай:**

```bash
python3 scripts/adapter_setup.py connect <тип> --name "<имя>" --base-url <адрес> --secret-file <имя-файла> [--alias <адрес>] --confirmed-by "<дословный ответ оператора>"
```

Команда создаёт подключение одним запросом к ядру и сразу проверяет его двумя способами: ядро само стучится во внешнюю систему, и скрипт делает запрос «кто я» через новое подключение.

**7. Скажи результат по выводу:**
- «ИТОГ: подключение работает» — назови адрес для агентов и учётную запись внешней системы из строки «Проверка запросом». Спроси оператора: «Это та учётная запись, под которой должны работать агенты?»
- «ИТОГ: подключение создано, но проверка НЕ прошла» — см. раздел 2.5. Не оставляй такое подключение без решения оператора: агенты уже видят его в списке.
- «Ядро отклонило» — ничего не создано; причина в той же строке.

## 2.5. Если что-то пошло не так

| Что напечатано | Что это | Что делать |
|---|---|---|
| «уже есть подключение этого типа … Задай свой короткий адрес» | защита общего короткого адреса (см. 2.4, п. 3) | спросить оператора, нужно ли второе подключение; если да — выбрать `--alias` |
| «Ядро отклонило: … alias … is already used» | короткий адрес занят | выбрать другой |
| «Ядро отклонило: … name already exists» | подключение с таким именем уже есть | взять другое имя или проверить существующее (`check`) |
| «Ядро отклонило: … не подходит адаптеру» / `invalid_secret` | ключ не той формы | сверить файл ключа со строкой «Секрет» из `describe`; оператор исправляет файл |
| «Проверка ядром: unhealthy … ответ внешней системы: HTTP 401» (или 403) | внешняя система не приняла ключ | оператор проверяет ключ. Затем `remove` и `connect` заново: поменять ключ у созданного подключения мастер не умеет |
| «Проверка ядром: unhealthy» без кода ответа | из инстанса нет связи с адресом системы или неверный адрес | проверить адрес с оператором; сеть инстанса до внешней системы — задача оператора |
| «для этого типа ядро не умеет проверять связь само — НЕ проверено» | у типа нет проверки | сказать «создано, не проверено»; попросить оператора назвать простой запрос на чтение и выполнить его вручную по адресу для агентов |
| «/api/adapters/connect → 404» или «не принимает вызов … без токена владельца» | эта версия или настройка ядра не даёт создавать подключения изнутри пода | раздел 2.6 |
| «обращение к ядру Gina через kubectl не удалось» | нет права `exec` или под недоступен | раздел 2.6 |

Убрать созданное подключение (только после слов оператора):

```bash
python3 scripts/adapter_setup.py remove --name "<имя>" --confirmed-by "<ответ оператора>"
```

Подключение уходит в архив, адрес для агентов снимается. Ключ остаётся в хранилище секретов инстанса: удалить его может только владелец инстанса — скажи это оператору. Подключения, созданные не мастером, команда не трогает без флага `--foreign`; не ставь его без прямого слова оператора о конкретном подключении.

## 2.6. Чего мастер на этом шаге не делает

Скажи оператору прямо, если это его случай:

- **Каналы общения** (чат, Mattermost, Telegram, почта) и **входящие очереди задач** (автоматический набор задач из трекера) мастер не создаёт: им нужны настройки привязки и решения оператора. Они настраиваются в интерфейсе Gina. Без канала общения просьбы людей до агентов не дойдут — это покажет шаг 3 и итоговая проверка.
- **Нет права `exec` или ядро не принимает вызов** — подключения создаёт оператор в интерфейсе Gina. Попроси его сделать это и после выполни `python3 scripts/adapter_setup.py list` (если работает) либо перейди к шагу 3: команда `project_probe.py detect` покажет подключения через внешний API.
- **Поменять ключ** у существующего подключения и **удалить ключ** из хранилища мастер не умеет: это действия владельца инстанса.
- **Права технической учётной записи** во внешней системе мастер не проверяет: проверка говорит только, что ключ принят. Хватает ли прав на репозитории и проект — выяснится на шаге 3 при исследовании кода и трекера.

## Завершение шага

```bash
python3 scripts/adapter_setup.py list
```

Покажи оператору итоговый список и назови: что подключено и проверено; что нужно проекту, но не подключено, и почему; что оператор взялся настроить сам.

- Всё, что оператор назвал нужным, подключено и проверено (или он осознанно отложил) — `python3 scripts/wizard_state.py step 2 done`.
- Осталось неподключённое, без которого агентам нечем работать (нет хостинга кода) — `step 2 partial "<что не подключено и почему>"`. Мастер можно продолжать: на шаге 3 соответствующие признаки будут выключены, и агентам прямо напишут, чего в установке нет.
