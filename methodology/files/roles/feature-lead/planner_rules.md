ПРАВИЛА ПЛАНИРОВЩИКА (POC)

Эти правила дополняют встроенную инструкцию планировщика. Они задают маршрут дела в проекте; механика шагов — встроенная.

МАРШРУТ ДЕЛА (минимальный цикл разработки):
1. Разбор — агент `analyst`. Вход: задача из трекера или просьба человека из чата. Выход: понятая задача, критерии приёмки, затронутые репозитории, план, открытые вопросы.
2. Реализация — агент `developer`. Вход: план разбора без открытых вопросов. Выход: ветка, коммиты, merge request, честный статус проверок.
3. Ревью — агент `reviewer`. Вход: merge request и критерии приёмки. Выход: вердикт «ЧИСТО» или «ЕСТЬ ЗАМЕЧАНИЯ» комментарием в merge request.
4. Передача человеку — merge request с вердиктом «ЧИСТО» передаётся ревьюеру-человеку, задача переводится в статус ревью, заказчику уходит итог. Вливает merge request и закрывает задачу только человек.

ПРАВИЛА МАРШРУТА:
- Один шаг — один агент — одно задание с понятным результатом. Не ставь реализацию, пока у разбора есть открытый вопрос к человеку.
- Замечания ревью возвращай тому же `developer` (новый круг: правка → повторное ревью только изменённого). Больше трёх кругов по одному merge request-у — остановись и сообщи человеку, что именно не сходится.
- Просьба без изменения кода (вопрос по проекту, справка, поиск причины) — один шаг `analyst`, без ветки и merge request-а; итог — ответ заказчику.
- Задача затрагивает несколько репозиториев — один merge request на репозиторий, реализация по одному репозиторию за шаг; порядок называет разбор.
- Навыки шагу выдавай по работе. Всем — `project` и `sdlc-workflow`. Любое сообщение человеку — `team-communication`. Правка кода и проверки — `development-and-testing`.
[если:gitlab]- Работа с репозиторием, веткой, merge request-ом — `gitlab`. Шаг запускает сборку и должен дождаться результата — `build-watch`.
[если:jira]- Задача из трекера — `jira`.
[если:code_conventions]- Правка и ревью кода — `code-conventions`.
[если:product_ui]- Задача про поведение интерфейса продукта — `product-ui`.

ОЖИДАНИЕ И ОТКАЗЫ СРЕДЫ:
- Исполнитель вернулся с ожиданием (сборка, ответ человека, стенд) — не ставь новый шаг вслепую: сначала убедись, что ожидаемое наступило.
[если:gitlab]- Ожидание сборки надёжно, только если исполнитель подал заявку `build-watch` и она есть в памяти инстанса (`GET http://gina-evd:8080/api/memory?kind=build-watch`). Заявки нет — дело никто не разбудит: поставь короткий шаг тому же исполнителю «подать заявку или прочитать сборку сейчас».
[если:gitlab]- Пришла побудка «сборка закончилась» — следующий шаг тому же исполнителю: прочитать сборку и продолжить по её итогу.
- Один и тот же отказ среды два захода подряд (нет исполнителя сборок, недоступен стенд, не создаётся сессия) и ветка при этом не изменилась — третий такой заход не ставь. Сообщи человеку: что не работает, с какого времени, что уже готово, — и жди.
- Очередь сборки («ждёт», «нет подходящего исполнителя») — это не зелёный и не красный вердикт. Не выдавай его за результат проверки.

ЗАВЕРШЕНИЕ:
- Дело завершено, когда выполнено всё из п. 4 маршрута, либо человек получил ответ на вопрос без изменения кода, либо человек отменил работу.
- Незавершённое не объявляй завершённым: если проверка не выполнена (сборки не работают, стенда нет) — так и напиши в итоге заказчику.
