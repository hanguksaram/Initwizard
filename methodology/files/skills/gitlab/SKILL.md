# GitLab через прокси Gina

Какие репозитории относятся к проекту, какая у них основная ветка и модель веток — в навыке `project`. Здесь — механика.

## Доступ

- API: `http://gina-evd:8080/gitlab/api/v4/...` — обычный API GitLab, учётные данные подставляет Gina. Токен в запрос не клади и не спрашивай.
- Клон и пуш — по HTTP через тот же адрес: `git clone http://gina-evd:8080/gitlab/<путь репозитория>.git`. Клонируй только нужный репозиторий, в свою папку захода, с `--depth 50`, если история не нужна.
- Актуальные адреса прокси и подсказка по использованию: `GET http://gina-evd:8080/api/adapters/binding-usage`.

## Проект — по точному пути

Числовой id бери запросом по полному пути (из навыка `project`), а не поиском по имени:

```bash
G=http://gina-evd:8080/gitlab/api/v4
curl -s "$G/projects/<группа%2Fподгруппа%2Fрепозиторий>" | jq '{id, path_with_namespace, default_branch}'
```

Сверь `path_with_namespace` с ожидаемым. Не совпал — стоп: это не тот проект.

## Ветка, коммиты, merge request

1. Ветка от свежей целевой; имя — по правилу из навыка `project`, раздел «Ветки» (не задано — `gina/<КЛЮЧ-ЗАДАЧИ>-<кратко-латиницей>`).
2. Коммиты небольшие; формат сообщения — по правилам репозитория
[если:code_conventions](навык `code-conventions`);
если правил нет — `<КЛЮЧ-ЗАДАЧИ>: <что сделано>`.
3. Перед пушем: `git diff --check`, саморевью диффа (нет лишних файлов, отладочного вывода, секретов).
4. Merge request в целевую ветку. Один merge request на задачу в одном репозитории.

Описание merge request-а:

```
## Задача
<ключ и ссылка на задачу или суть просьбы>

## Что изменено
<по пунктам, языком результата>

## Как проверено
<команды и их итог; сборка: ссылка и статус. Не проверено — что и почему>

## На что посмотреть ревьюеру
<риски, спорные места; «нет», если нет>
```

Вливать merge request, пушить в основную ветку и в теги нельзя — это делает человек.

## Сборка: читай статус, не угадывай

```bash
curl -s "$G/projects/<id>/pipelines?ref=<ветка>&per_page=3" | jq '.[] | {id, status, sha: .sha[0:8]}'
curl -s "$G/projects/<id>/pipelines/<pid>/jobs?per_page=50" | jq '.[] | {name, stage, status, failure_reason}'
```

- Пустой список — сборки нет. Это не «зелёная».
- `failure_reason` = `stuck_pending_no_matching_runners` или шаг висит в `pending` — исполнителя сборок нет: «CI недоступен».
- `success` всей сборки при `allow_failure` у упавшего шага — смотри шаги, а не общий статус.
- Сборка идёт дольше одного вызова — не жди циклом: подай заявку на побудку (навык `build-watch`) и заверши заход с ожиданием и номером сборки.
