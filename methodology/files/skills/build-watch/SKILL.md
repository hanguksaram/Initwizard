# Заявка на побудку по окончании сборки

## Зачем

Пайплайн идёт минуты или десятки минут. Ждать его внутри захода нельзя: цикл с паузой сжигает заход. Вместо этого дело оставляет **заявку** и засыпает; регламент «СТОРОЖ СБОРКИ» раз в минуту смотрит пайплайн заявки и, когда тот дошёл до конца, кладёт в дело входящее со статусом — дело просыпается.

## Сначала проверь, что сторож включён

```bash
curl -s http://gina-evd:8080/api/automations | jq -r '(.items // .automations // .)[] | select(.name == "СТОРОЖ СБОРКИ") | .state'
```

- `armed` — подавай заявку.
- Что угодно другое или пусто — заявку **не подавай**: её никто не разберёт. Заверши заход с ожиданием и напиши прямо: «жду пайплайн <номер>; автоматической побудки нет — сторож сборки не включён».

## Порядок: заявка → пуш → номер пайплайна

**1. Заявка — ДО пуша.** Коммит уже известен (голова твоей ветки), а пуш необратим: если заход оборвётся между пушем и заявкой, сборка останется без хозяина.

```bash
M=http://gina-evd:8080/api/memory
NB=$(date -u +%Y-%m-%dT%H:%M:%SZ)                       # граница: мой пайплайн новее этого момента
EXP=$(date -u -d '+60 minutes' +%Y-%m-%dT%H:%M:%SZ)     # срок заявки
SHA=$(git rev-parse HEAD)                                # только полный хэш, 40 символов
curl -s -X POST $M -H 'Content-Type: application/json' -d "$(jq -n \
  --arg sc "<SC_ID из задания захода>" --arg task "<ключ задачи>" --argjson pid <числовой id репозитория> \
  --arg ref "<ветка>" --arg sha "$SHA" --arg nb "$NB" --arg exp "$EXP" --arg note "<что запускаю и зачем>" \
  '{data: {kind: "build-watch", sc_id: $sc, task: $task, project_id: $pid, ref: $ref, sha: $sha, pipeline: null, not_before: $nb, expires_at: $exp, note: $note}}')" | jq '{id}'
```

Сразу перечитай заявку и убедись, что она есть: `curl -s "$M?kind=build-watch" | jq '.items[] | {id, data}'`. Если формат тела отклонён — прочитай текст ошибки и поправь по нему; способ записи в память анклава описан во встроенной инструкции платформы.

**2. Пуш** (или действие, запускающее пайплайн).

**3. Допиши номер пайплайна.** Найди пайплайн своего коммита (навык `gitlab`) и запиши его номер в заявку: `PATCH $M/<id заявки>` с телом `{"data": <заявка целиком с pipeline: номер>, "expected_updated_at": "<updated_at из последнего чтения заявки>"}`. Запись заменяет `data` целиком — отправляй все поля, а не только изменённое. С номером сторож смотрит ровно этот пайплайн и не гадает по коммиту. Пайплайн за пару минут не появился — оставь `pipeline: null`: сторож найдёт его по `sha` и `ref`, а если не найдёт до срока — разбудит честным текстом.

**4. Заверши заход ожиданием:** что ждёшь (проект, ветка, коммит, номер пайплайна), номер заявки, что делать после побудки.

## Поля заявки

| Поле | Значение |
|---|---|
| `kind` | всегда `build-watch` |
| `sc_id` | дело, которое будить: значение `SC_ID` из текста задания захода. Не выдумывай и не бери из окружения |
| `project_id` | числовой id репозитория (по точному пути, навык `gitlab`) |
| `ref` | ветка, в которой пойдёт пайплайн |
| `sha` | полный 40-символьный хэш коммита; по короткому GitLab пайплайн не находит |
| `pipeline` | номер пайплайна или `null`, пока неизвестен |
| `not_before` | текущее время перед подачей; пайплайны старше этой границы (прошлые попытки на том же коммите) сторож пропускает |
| `expires_at` | срок заявки: обычная длительность пайплайна репозитория плюс запас; не знаешь длительность — 60 минут |
| `job` | необязательно: номер джобы, если ждёшь перезапуск одной джобы в уже завершённом пайплайне |
| `task`, `note` | для человека, читающего память: задача и что ждём |

## Что придёт после побудки

Входящее вида «Сборка коммита <sha>: пайплайн <номер> (проект, ветка) — success | failed | canceled | skipped | manual» либо «…не закончилась за срок заявки: …». После побудки:

1. Перечитай пайплайн и джобы сам (навык `gitlab`): побудка — повод посмотреть, а не вердикт.
2. `failed` — разбери упавшие джобы: это твоя правка, чужая поломка или среда. Среда (нет раннера, недоступен образ) — «CI недоступен», а не «красный».
3. «Пайплайна так и нет» — значит, CI на эту ветку не запускается или раннера нет: запиши это в итог, повторно ту же заявку не подавай.
4. Заявка после побудки снята. Нужен ещё один круг ожидания — новая заявка с новым `not_before`.

## Чего не делать

- Не жди пайплайн циклом внутри захода «на всякий случай» рядом с заявкой.
- Не подавай вторую заявку на тот же коммит, пока жива первая.
- Не удаляй чужие заявки и не трогай записи памяти с другим `kind`.
