# Маршрут дела: разбор → реализация → ревью → передача

## 1. Разбор (analyst)

Вход: задача из трекера или просьба человека.

Сделай:
1. Прочитай постановку целиком: задачу со всеми комментариями или ветку разговора.
2. Найди затронутый код: какие репозитории и файлы, как сейчас работает (навык `project`). Код только читай.
3. Запиши план на стол дела и коротко — в задачу или в ветку разговора:

```
Понял задачу так: <1–3 фразы>
Критерии приёмки:
1. <проверяемое утверждение>
Затронуто: <репозиторий: файлы или модули>
План: <шаги реализации; порядок репозиториев, если их несколько>
Проверка: <какими тестами и командами; что проверить нельзя и почему>
Открытые вопросы: <нет | вопрос>
```

Готово, когда критерии приёмки проверяемы и открытых вопросов нет. Есть вопрос, меняющий состав или объём работы, — задай его (навык `team-communication`) и жди ответа.

## 2. Реализация (developer)

Вход: план без открытых вопросов.

Сделай:
1. Ветка от свежей целевой.
2. Минимальная правка под критерии приёмки. Стиль — по правилам репозитория
[если:code_conventions](навык `code-conventions`)
и как в соседнем коде. Тест рядом с изменённой логикой, если в репозитории есть тесты такого рода.
3. Проверки по навыку `development-and-testing`.
4. Пуш, merge request с описанием: задача, что изменено, как проверено, на что посмотреть. Статус сборки прочитан.
[если:gitlab]   Сборка идёт — заявка на побудку (навык `build-watch`) и ожидание; после побудки дочитай итог и обнови описание merge request-а.
5. Задача в трекере: статус «в работе» в начале (если такой переход разрешён агенту), комментарий со ссылкой на merge request.

Готово, когда merge request открыт, каждый критерий приёмки закрыт правкой или назван незакрытым с причиной, статус проверок честный.

## 3. Ревью (reviewer)

Вход: merge request и критерии приёмки.

Сделай:
1. Прочитай дифф целиком и окружающий код, а не описание merge request-а.
2. Сверь с каждым критерием приёмки. Ищи: поведение не по постановке, сломанные соседние сценарии, отсутствие проверки ошибок, секреты и лишние файлы, непроверенные утверждения в описании.
3. Оставь вердикт комментарием в merge request:

```
ВЕРДИКТ: ЧИСТО | ЕСТЬ ЗАМЕЧАНИЯ
Блокирующие: <нет | список: файл:строка — что не так — что ожидается>
Важные: <…>
Мелочи: <…>
Критерии приёмки: 1 — закрыт / не закрыт (<почему>)
```

Код не правь: ревьюер выносит вердикт, исправляет разработчик. Повторное ревью — только изменённое с прошлого круга.

## 4. Передача человеку

Когда вердикт «ЧИСТО»: merge request назначен ревьюеру-человеку (кто это — из задачи; не указан — ревьюер по умолчанию из навыка `project`), задача переведена в статус ревью (если такой переход разрешён агенту), заказчику ушёл итог (навык `team-communication`). Вливает и закрывает задачу человек.

## Размер

Одна задача — один merge request на репозиторий. Правка разрослась за пределы плана — остановись и верни на разбор, а не расширяй merge request молча.
